## Executive Summary

The site is in solid technical shape for a brochure-class build: clean URL structure, canonicals, single H1 per page, dynamic sitemap, JSON-LD `LocalBusiness`, WebP imagery, lazy-loaded below-the-fold media, and font preloading. The scaffolding is doing real work — but the SEO model is "small contractor homepage," not "regional services business with multiple yards and four discrete service lines." That mismatch is the single biggest opportunity.

**Top three high-impact opportunities:**

1. **Promote service and equipment items from in-page anchors to real URLs.** The four services and four equipment categories currently exist only as anchor sections on `/services/` and `/equipment/` (e.g. `/services/#bmp-management`). They cannot rank independently, cannot accumulate links, cannot carry their own meta/OG/schema, and cannot be entry points for long-tail queries like "concrete washout contractor Florida" or "construction street sweeping Umatilla." This is a one-time architecture change with compounding payoff.
2. **Move from generic `LocalBusiness` to `GeneralContractor` (a `HomeAndConstructionBusiness` subtype), add per-service `Service` schema, add `Organization`, `WebSite`, and `BreadcrumbList`, and stop emitting the LocalBusiness JSON-LD on every interior page.** The current schema is correct but generic and duplicated site-wide; the more specific type and per-page schema give Google sharper signals for the construction vertical and service-area queries.
3. **Build dedicated location landing pages for Umatilla, Palm Coast, and Moore Haven, and tighten geo signals.** The three "locations" are referenced only as plaintext mentions and `areaServed` cities. The site has zero crawlable surface for "[service] + [city]" queries, which is exactly how this market searches. Combine with a Google Business Profile for each yard (out of scope here but feeds the same surface).

The site is well above average on technical hygiene and well below average on content depth and information architecture. The fix list below is small but high-leverage.

### 2. Technical SEO

#### 2.1 Canonical

`base.njk:12` — self-referencing canonical built from `site.url + page.url`. Verified in `/public/index.html:7`, `/public/about/index.html:7`, `/public/services/index.html:7`. Correct.

#### 2.2 Sitemap

`src/sitemap.njk` (template) → `/public/sitemap.xml` (built):

```xml
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
      <url><loc>https://walkerbldgcorp.com/about/</loc><lastmod>2026-05-13T17:54:17.256Z</lastmod><changefreq>monthly</changefreq></url>
      ...
      <url><loc>https://walkerbldgcorp.com/</loc><lastmod>2026-05-14T16:00:38.189Z</lastmod><changefreq>monthly</changefreq></url>
</urlset>
```

Findings:
- The XML declaration is preceded by a blank line in `public/sitemap.xml:1`. Some strict parsers reject XML with leading whitespace before `<?xml ?>`. Search Console will likely accept it, but it's worth fixing. The blank line is caused by the front-matter block in `src/sitemap.njk:1-4` — change `{%- for ... %}` style trimming or set Nunjucks output to trim leading whitespace.
- `lastmod` is set to the file's build/modification time via the `isoDate` filter (`eleventy.js:21`). That equals the build timestamp, not the actual content edit date. After every deploy, every URL appears freshly modified, which trains Google to ignore the value. Either use the Markdown file's frontmatter `date` (and require editors to set it) or use git's last-commit date for the file.
- `priority` is omitted entirely. Google ignores it, but most other crawlers and validators expect it; not critical.
- `changefreq` is hardcoded `monthly`. Also largely ignored by Google. Fine.
- Sitemap does not include `/contact/thanks/` (probably correct, but verify the page exists somewhere — referenced by both forms).
- No image sitemap or extension entries, despite a video-heavy hero treatment and meaningful product imagery.

#### 2.6 Performance Signals (from static output)

- WebP for all content imagery — confirmed in service and equipment frontmatter.
- Font preloading with `crossorigin` — correct (`base.njk:28-29`).
- `<link rel="stylesheet" href="/assets/css/main.css">` — single CSS file, render-blocking. Acceptable for a 6-page site.
- Hero video: `preload="metadata"`, `autoplay muted playsinline loop`. The hero `<video>` is the LCP candidate on every page since it's above the fold. A `<video>` element typically is **not** counted as LCP — the LCP element on each page is whatever poster fallback or visible text loads first. The hero partial (`hero.njk:23`) supports `hero.poster` for video fallback, but no page sets `hero.poster`. Without a poster, mobile users on slow connections see a blank black box until metadata loads. Add a poster image (WebP, well-compressed) per hero. This also improves LCP scoring directly.
- Hero videos: I see no compression details and no `<source>` for WebM. mp4 only at `/assets/video/hero-*.mp4`. If these are >1 MB each, Core Web Vitals on mobile will suffer. Recommend serving compressed mp4 ≤ 1 MB and considering not autoplaying on small viewports (CSS media query swap to a static poster on mobile).
- All content images `loading="lazy"` — good. The hero is not an image so the LCP-image-eager-loading rule doesn't apply, but if you switch to a poster, do **not** lazy-load that one.
- Images lack `width`/`height` and `decoding="async"` (other than logos). Add both.
- `theme-color` set (`base.njk:23`). Good.
- No `<link rel="dns-prefetch">` or `<link rel="preconnect">` to any third party — likely unnecessary given there are no third-party scripts, fonts, or analytics in the head. Confirm whether GA4 / GTM lives elsewhere (e.g. injected by Cloudflare) and whether it's accounted for.

### 3. Structured Data

#### 3.1 Current Implementation

`src/_includes/layouts/base.njk:32-61` emits a single JSON-LD block on every page:

```json
{
  "@context": "https://schema.org",
  "@type": "LocalBusiness",
  "name": "Walker Building Corporation",
  "url": "https://walkerbldgcorp.com",
  "telephone": "+13527712651",
  "email": "Info@WalkerBldgCorp.com",
  "image": "https://walkerbldgcorp.com/assets/img/logo.webp",
  "address": { ... },
  "geo": { ... },
  "openingHours": "Mo,Tu,We,Th,Fr 08:00-16:00",
  "areaServed": [ ... ]
}
```

What's right:
- Valid JSON-LD, validates against schema.org `LocalBusiness`.
- `address` is a proper `PostalAddress` with all required fields.
- `geo` includes lat/lng.
- `openingHours` uses the correct day-token format.
- `areaServed` uses `City` objects (acceptable, though `AdministrativeArea` or `Place` with geo would be richer).
- `image` is absolute.

What's missing or weak:

- **Type is too generic.** `LocalBusiness` is the parent class. For a construction company, the schema.org chain `LocalBusiness > HomeAndConstructionBusiness > GeneralContractor` is more specific and gives Google a sharper category signal. Use `"@type": "GeneralContractor"`.
- **No `@id` for entity reconciliation.** Add `"@id": "https://walkerbldgcorp.com/#organization"` so other schema blocks can reference the same entity.
- **No `priceRange`.** `LocalBusiness` recommends this property (use a generic `"$$"` or similar).
- **No `sameAs` array.** Even with `site.social` empty in `site.json:35`, the schema should still reference any Google Business Profile, BBB listing, or industry directory profile (Procore, etc.) once they exist.
- **No `logo` property.** `image` is set, but Organization-type entities should also declare `logo` (with an `ImageObject` ideally — and Google requires a `logo` for the "Organization" knowledge panel image to be considered).
- **No `numberOfEmployees`, `foundingDate`, or `slogan`** — recommended for `Organization` subtypes; help with knowledge-panel population.
- **`areaServed` could be modeled as `GeoCircle` or `Place` with bounding `geoRadius`** in addition to the cities, especially since service area is the business model. Three city pins is acceptable; bounding geometry is stronger.
- **Schema is emitted on every page, identical.** That's fine for the homepage, but on `/services/` you should have a `Service` graph; on `/about/` you should have an `AboutPage` + `Organization`; on `/contact/` a `ContactPage`. Use `@graph` to combine multiple entities per page.
- **No `Service` schema for any of the four service lines.** This is a major miss. Each service should declare a `Service` entity with `serviceType`, `provider` (referencing the org `@id`), `areaServed`, and `description`. When the services move to their own URLs (P0 below), this becomes especially important.
- **No `BreadcrumbList`.** Breadcrumb rich results require this. Even a flat `Home > Services` breadcrumb is worth marking up, and becomes mandatory once second-level service URLs exist.
- **No `Organization` separately declared.** Google Search Central recommends a top-level `Organization` (or its subtype) on the homepage with `logo`, `url`, and `sameAs`. Walker can satisfy this by making the LocalBusiness/GeneralContractor entity also play the Organization role, but the homepage should declare it explicitly.
- **No `WebSite` schema** with `SearchAction` (sitelinks search box). Not urgent for a 6-page site, but trivial to add.
- **No `FAQPage`** anywhere. There are no FAQ blocks on the site currently, but the construction-services vertical has heavy "People Also Ask" volume (e.g. "what is a BMP," "do I need a SWPPP," "how often should construction sites be swept"). Adding an FAQ section per service page with `FAQPage` schema is a featured-snippet play.

#### 3.2 Recommended Schema Set (Final State)

- Homepage: `@graph` containing `GeneralContractor` (with full address/geo/areaServed), `Organization` (with `sameAs`, `logo`), `WebSite` (with `potentialAction` SearchAction if site search exists; otherwise omit), `BreadcrumbList`.
- Service pages (once they exist): `Service` + `BreadcrumbList` + optional `FAQPage`.
- Equipment pages (if created): `Product` is overkill since these are owned fleet, not inventory; stick with the parent `Service` schema referencing equipment in `description`.
- About: `AboutPage` + reference to `Organization` `@id`.
- Contact: `ContactPage` + repeat `GeneralContractor` reference.

### 4. Local SEO

#### 4.1 NAP (Name, Address, Phone) Consistency

NAP appears in:
- `site.json:2-3` — full and short name. **Both forms are used** — the JSON-LD uses "Walker Building Corporation", the title tag short suffix uses "Walker Building Corp", the footer logo alt uses the full name. Pick one canonical legal name and use it consistently in structured data and citations. The footer copyright (`footer.njk:43`) uses full name; correct.
- `header.njk:10-12` and `footer.njk:34-37` — same address.
- `section-contact-form.njk:20-23` — same address.
- Phone is `+13527712651` (E.164) in `tel:` links and JSON-LD; displayed as `(352) 771-2651`. Consistent.
- Email: `Info@WalkerBldgCorp.com` — note the mixed case. Email addresses are case-insensitive in the local part per RFC 5321 §2.3.11 but are often presented lowercase. Google parses it correctly either way. Not a problem, just a stylistic note.

NAP consistency on the site itself is solid. The off-site challenge (GBP, Apple Maps, Bing Places, Yelp, BBB, industry directories) is out of scope but is where local rankings actually live.

#### 4.2 Service-Area Markup

- `areaServed` lists three cities: Umatilla, Palm Coast, Moore Haven (`site.json:26`).
- Geographically, these three cities are far apart: Umatilla (central FL, Lake County), Palm Coast (east coast, Flagler County, ~80 miles east), Moore Haven (south-central FL, Glades County, ~130 miles south). That is the entire I-4 corridor and points south — a much larger service area than three city tags imply. Consider listing surrounding counties (Lake, Marion, Volusia, Flagler, Glades, Hendry) and key cities in each yard's radius (Ocala, Orlando, Daytona Beach, Clermont, LaBelle, Sebring, etc.) for `areaServed`.
- About page mentions "central and east-central Florida" (`about.md:23`). Schema doesn't reflect that breadth.

#### 4.3 Geo Coordinates

`site.json:18-19` — lat 28.9472, lng -81.6664. That is the Umatilla yard area. Verify against actual yard address (1079 Duck Box Rd, Umatilla, FL 32784). A quick check: Umatilla is roughly 28.92°N, 81.66°W, so the coordinate is plausibly correct (it's the office, not the geographic center of the service area). Acceptable.

Note: with three yards, you have three `Place`s to mark up. The `LocalBusiness` schema can only carry one `address` and one `geo` for the legal entity. The Palm Coast and Moore Haven yards should each become a `Place` entity with their own address/geo, linked from the parent via `subOrganization` or, more correctly, modeled as separate `LocalBusiness` instances on dedicated location pages.

#### 4.4 Location Landing Pages

**There are zero.** This is the biggest local SEO gap. For each yard:
- `/locations/umatilla/`
- `/locations/palm-coast/`
- `/locations/moore-haven/`

Each page should carry: address, hours, phone (centralized is fine), embedded map, service area description, equipment available locally, photos of the yard, key projects in that region, and a `LocalBusiness` or `GeneralContractor` schema block scoped to that location. These pages capture "[service] [city]" queries that the current site cannot rank for.

#### 4.5 Hours of Operation

`site.json:21-25` — Mon-Fri 8AM-4PM, weekends closed. Schema spec `"Mo,Tu,We,Th,Fr 08:00-16:00"` is correct.

Note: the JSON-LD uses `openingHours` (string format). The newer recommended property is `openingHoursSpecification` with `OpeningHoursSpecification` objects, which Google parses more reliably and supports special hours/holidays. Migrate when convenient.

### 5. Social / Open Graph

`base.njk:14-22`:

```html
<meta property="og:type" content="{% if page.url == '/' %}website{% else %}article{% endif %}" />
<meta property="og:title" content="{{ pageTitle }}" />
<meta property="og:description" content="{{ pageDesc }}" />
<meta property="og:url" content="{{ absUrl }}" />
<meta property="og:site_name" content="{{ site.name }}" />
{%- if ogImage %}
<meta property="og:image" content="{{ site.url }}{{ ogImage }}" />
{%- endif %}
<meta name="twitter:card" content="summary_large_image" />
```

Issues:

- **`og:type` "article" is wrong for interior service/about pages.** Use `website` for all pages on a marketing site. `article` is appropriate for blog posts only. Right now `/about/`, `/services/`, `/equipment/`, `/careers/`, and `/contact/` all advertise themselves as articles, which can trigger inconsistent rendering on Facebook/LinkedIn/Slack.
- **`og:image` is conditional and never set.** No page in `src/content/pages/*.md` declares `ogImage` in frontmatter. The result: zero pages have an OG image. Verify by inspecting `/public/*/index.html` — no `og:image` line is rendered. **This is the highest-visibility quick win.** When the site is shared in Slack, iMessage, Facebook, LinkedIn, or X, it renders with no image card.
- **`twitter:card` is `summary_large_image`** but with no `og:image`, Twitter falls back to a plain summary card. Once OG image is set, this works.
- **No `twitter:title` or `twitter:description`** — these aren't required (Twitter falls back to OG values), but explicit declarations are best practice.
- **No `og:locale`** (defaults to `en_US`, usually inferred correctly from `<html lang="en-US">`, but explicit is better).
- **No fallback site-wide OG image.** Set a default in `site.json` (e.g. `/assets/img/og-default.webp` — a branded composition with logo and tagline) and use it whenever `ogImage` isn't set per page. Recommended dimensions: 1200x630 px, < 5 MB, WebP or JPG. (Note: Facebook officially recommends JPG/PNG for OG. WebP works on most platforms but Facebook's debugger sometimes still has trouble — use 1200x630 JPG for safety.)
- **No per-page `ogImage`** — once a default is in place, override per page with relevant imagery (e.g. `/services/` uses the BMP installation photo).

## Keyword Opportunity Notes

This is light-touch directional analysis — pull volumes from a paid tool (Ahrefs, Semrush) before committing to a content calendar.

### Branded
- "walker building corporation," "walker building corp" — low volume, already owned. Defend with consistent NAP and a fleshed-out homepage.

### Service-Line (primary)
- "erosion control contractor [city]" — high commercial intent. Florida-specific volume is meaningful given the I-4 corridor's construction activity. Target with services hub + per-service pages + location pages.
- "BMP installation contractor" / "stormwater BMP management Florida" — niche but high-intent.
- "SWPPP compliance Florida" / "NPDES contractor Florida" — informational + commercial. Pairs well with a blog post explaining requirements, then funneling to the BMP service page.
- "concrete washout services Florida" — niche, mid-volume, very high intent.
- "construction street sweeping [city]" — clear commercial intent; differentiate from janitorial street-sweeping services.
- "silt fence installation [city]" — long-tail under BMP umbrella.
- "turbidity barrier installation Florida" — niche, often paired with marine/waterfront construction.
- "post-storm debris removal contractor Florida" — seasonal, hurricane-driven spikes. Worth an evergreen page that ranks ahead of storm season.

### Equipment / Capability
- "skid steer rental [city]" — Walker is owner-operator, not rental, but a content page can capture searches that filter out as wrong-fit and reach the ones looking for contracted operators. Be careful here: don't accidentally rank for "rental" if you don't rent.
- "tri-axle dump truck contractor Florida" — niche.
- "construction site cleanup services central Florida" — broad commercial.

### Geo-Modified (highest opportunity for a regional contractor)
- "[service] Umatilla / Palm Coast / Moore Haven" — low volume individually, but the local pack is winnable with proper GBP + location pages + on-page geo.
- "[service] Lake County FL," "[service] Flagler County FL," "[service] Glades County FL" — wider net.
- "[service] Ocala / Leesburg / Mount Dora / Eustis / Tavares / Clermont / Daytona / Bunnell / LaBelle" — secondary city targets within each yard's drive radius. Worth one location page per **yard** initially, with surrounding cities mentioned and internally linked.

### Informational (top-of-funnel, for future blog)
- "what is a BMP in construction"
- "do I need a SWPPP for my project Florida"
- "FDOT erosion control standards"
- "how often should construction sites be swept"
- "construction concrete washout disposal rules"

### Careers
- "construction jobs central Florida," "CDL driver jobs Umatilla," "heavy equipment operator jobs Florida" — should land on `/careers/`. Today the page exists but has minimal content beyond a form. Add job-listing detail and `JobPosting` schema (per open role) to capture Google for Jobs surface.

### Competitive context
There are 1,800+ erosion-and-sediment-control contractors listed in Florida on Procore. The Central Florida vertical is contested (Absolute Erosion Control, Wind River Environmental / Brownie's, Rogers Environmental, Cypress EI, etc.). Differentiation comes from (a) location coverage breadth, (b) content depth on SWPPP/NPDES compliance, (c) crew-and-equipment proof, and (d) GBP/review velocity. The site is positioned to compete on (a) and (c) but needs the URLs and content to exist before any of that lands in SERPs.
